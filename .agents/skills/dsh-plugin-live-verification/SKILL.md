# 在真机上验证一个 DSH 插件

插件在单元测试里全绿、在真机上却「装上了但用不了」，是这类开发最常见也最贵的故障。原因不是逻辑写错，而是**宿主契约没满足**——契约不满足时宿主往往只打一行日志、把功能悄悄摘掉，命令和 HTTP 接口照常工作，从外部看就像一切正常。

这个 skill 教的是**怎么把「能用」变成一个可客观读到的数字**。它不提供命令清单：装什么、跑什么、用什么包管理器，一律按目标仓库自己的 `AGENTS.md` / `CONTRIBUTING` 决定。

## 一、先读宿主源码，别读文档

契约写在宿主包里，不在任何介绍文章里。宿主的安装目录下有 `node_modules/@deepseek-ai/dsh-*` 这些包，它们就是权威：

- `dsh-tools`：工具定义、schema 子集、执行流水线（参数校验 → `execute` → 返回值快照与 schema 校验 → `render` → 渲染结果快照 → 发布结果）。
- `dsh-skill`：技能注册表、`register()` / `get()` 的字段校验。
- `dsh-llm`：内容块（`ContentBlock`）类型与消费方，很多「下游崩」的根因在这里。
- `dsh-app-boot`（或同级的启动/加载器包）：模块解析、peer 注入。

**每条结论都要能指到 `文件:行号`**，写进报告或注释。凭印象写下的契约，下一代宿主就会打你的脸。契约本身也会变，所以 skill、注释里写的是「当时实测到的形态」，不是合同——动手前重新读一遍当前安装的那份。

## 二、工具过宿主，要过四道关

模型可见工具（`ctx.tools.register(defineTool(...))`）任何一道不过，就是整条链断掉。

### 1. 宿主包必须写进 `peerDependencies`

宿主的 loader 只在**插件自己的 `package.json` 声明过这个 peer** 时才会注入它。启动器里的 `readPeerNames(dir)` 读的就是被解析目录的 `package.json` 的 `peerDependencies` 键集合，没声明就构造不出注入路由，于是 `import '@deepseek-ai/dsh-tools'` 直接 `MODULE_NOT_FOUND`。

- 版本范围只写**开放下界**：写上界会让 loader 命中 profile 里装着的旧拷贝，版本检查失败并把插件停用。
- 宿主内置的包放进 `peerDependencies`，并在 `peerDependenciesMeta` 标 `optional: true`，避免自动装 peer 时在本地装一份物理副本。
- 源码里用动态 `import()` 并留降级路径：拿到宿主包再注册工具，拿不到就退化成「只有 HTTP/UI，没有工具」并**把这件事暴露成状态**（见第三节）。
- 判断「宿主到底有没有内置某个包」，别猜：从插件目录 `createRequire` 试一次解析。解析不到就说明只能靠注入，为它再押一个 peer 未必划算。

### 2. 工具返回值必须是 lossless JSON

流水线在 `execute` 之后会快照返回值，`undefined` 成员、函数、`Map`、类实例、稀疏数组都让快照失败，整次调用报错。典型写法错误是「可选字段赋 `undefined`」：

```js
// 坏：warning 为空时整次调用失败
return { id, warning: maybeWarning }
// 好：没有就不带这个键
return { id, ...(maybeWarning ? { warning: maybeWarning } : {}) }
```

注意 `null` 也不一定是替代品——如果 schema 里该字段是 `string`，`null` 会过不了输出 schema 校验。**「键不存在」才是缺省的正确表达。**

同一个位置还有一条容易漏的：**输出 schema 里的 object 节点必须显式写 `additionalProperties: true|false`**，宿主不接受「没写」这种开放缺省，编译 schema 时就报错。schema 只支持一个很小的关键字子集（`type` / `oneOf` / `properties` / `required` / `additionalProperties` / `items` / `enum` / `const` 加注释字段），写之前先看 `dsh-tools` 支持清单，别按 JSON Schema 的完整印象写。

### 3. `output.render` 必须返回 `ContentBlock[]`

`render(args, value)` 的返回类型是内容块数组，例如 `[{ type: 'text', text }]`。返回一个裸字符串**能通过快照**（字符串是合法 JSON），但下游消费内容块的地方会直接崩：判断是否含图片的 `contentHasImage()` 做的就是 `content.some(...)`，字符串没有 `.some`，于是**这个工具的每一次调用都失败**。

一个包内共用的 `textBlock(text)` 小助手能一次性堵住这类手误，值得写。

### 4. `skills.register` 必须自己传 `source`

宿主 `register()` 只给 `provider` 和 `invocation` 兜默认值，**`source` 不兜**。注册当下不校验它，所以注册「成功」了；等到真正加载技能正文时，定义校验会以 `loaded skill "<name>" source must be a string` 失败——错误信息里的 `loaded` 就是线索：问题在读取路径，不在注册路径。

随包分发的技能，统一用一个格式的来源标识（例如 `<包名>:<技能名>`），不要留空字符串。

注意这条和上面 `additionalProperties` 一样，属于**「注册时不报、读取时才炸」**的一类：判断某个字段到底必不必填，看 `register()` 的默认值合并逻辑，也看 `get()` 走的定义校验，两处都要读，别只读一处就下结论。

## 三、静默降级是最大的坑

宿主的常态是「优雅降级」：没有 `tools` 服务就不注册工具，`import` 失败就吞掉异常打一行 `console.error`。于是真机表现是——**命令说成功了，agent 手里却一个工具都没有**。这种故障最贵，因为它不报错。

对策是把状态变成**可被外部读到的字段**：

- 插件暴露一个状态接口，里面带类似 `toolsRegistered: true|false` 的布尔值，语义是「这批工具要么全注册上、要么一个都没上」。
- 注册是**全有或全无**：中途失败要把已注册的撤掉，再翻状态位。只注册一半却报「失败」，比一个都没注册更难查。
- 验证时**只认这个字段，不采信 agent 的自述**。agent 说「我调用了工具」可能只是在描述它以为发生过的事。

同理，注册技能的条数、HTTP 路由是否挂上，都应该有一个可读的计数或布尔，而不是只能从日志里猜。

### 假 ctx 测不出 inject 违规——这是离线全绿与真机可用的那道缝

写测试时用普通对象冒充 `ctx`（`{ get: () => ..., effect: (fn) => fn(), inject: () => {} }`）是常态，但它**结构上不可能复现宿主 ctx 的约束**。宿主的 ctx 是 Proxy：服务不是普通属性，而是通过 `ctx.mixin()` 注册的 **accessor**，读它会进 `get` 陷阱。

实测三种读法（同一段代码，普通对象 vs 真 ctx）：

| 读法 | 假 ctx（普通对象） | 真 ctx，未声明该服务依赖 |
| --- | --- | --- |
| `typeof ctx.interval` | `'function'`（骗过判断） | **抛 `cannot get property "timer" without inject`** |
| `ctx.get('timer')` | 看假对象怎么编的 | 正常返回服务对象 |
| `ctx.interval`（声明过依赖后） | `'function'` | `'function'` |

所以**`typeof ctx.xxx` 这种探测在假 ctx 上永远为真、在真 ctx 上可能直接抛**——离线测试会稳定通过，真机一加载就整个插件 `apply` 失败。而 `apply` 抛错的后果不是「这个功能不可用」，是**插件所有路由、所有工具、所有技能一个都没注册**，界面上表现为整片 404，很容易被误判成「宿主没加载新代码」。

几条实操结论：

- **探测可选服务用 `ctx.get(name)`，不要用 `typeof ctx.name`。** `get` 是 reflect 服务的普通方法，返回 `undefined` 而不抛。
- **要等某个服务就绪，用 `ctx.inject([name], (scope) => ...)`**，回调里的 `scope` 已经声明了依赖，此时读 `scope.name` 合法。
- **`ctx.effect` 不需要 inject**（它是 fiber mixin，任何 ctx 都有）；但**通过服务方法拿到的能力，作用域归谁要想清楚**。timer 这类服务返回的 disposer 会在它自己的 fiber 卸载时自动清掉，所以「我拿 disposer 手动释放」和「等宿主卸载」是两条路，两条都要能走通。
- **别把「探测失败」写成静默 `catch` 之后继续跑**：`try { typeof ctx.x } catch {}` 会把这个违规吞掉，让插件带着半死的状态启动。要么用 `ctx.get` 明确判空并写下状态原因，要么让它响亮地失败。
- **补一条能复现代理约束的用例**：用真 Cordis `Context` 加最小插件构造，而不是手搓普通对象；至少有一条断言「未声明依赖读服务属性会抛」。没有这条，187 条全绿也不能证明插件在真机上能加载。

## 四、路径判断必须走环境变量

开源产物里**不能出现本机绝对路径**。数据根这类宿主既有概念，要从宿主自己的环境变量派生（如 `DSH_HOME`），其余路径用自己的配置项 + 中性缺省（临时目录之类）。

几条踩过的细节：

- **要写成惰性函数，不要写成模块级常量。** 模块级常量在 `import` 那一刻就把环境冻住了：同一进程里改环境变量测不出来，测试和消费者也换不了环境。每次调用现取环境才对。
- **`~` 要自己展开，用 `homedir()`，不要读 `process.env.HOME`。** 而且展开必须在 `resolve()` **之前**——`resolve('~/x')` 会把它当相对路径，于是数据根跟着进程的当前工作目录漂移。这个 bug 只在从别的目录启动时才显形，非常隐蔽。
- **空白字符串按「未设置」处理**（`trim()` 后判空），不要当成一个叫空白的路径。
- 缺省值要和宿主的语义一致。宿主未设置时回落 `~/.dsh`，插件就不该回落某个具体机器上的目录。
- 路径包含关系判断要**分隔符安全**（用 `relative()` 判，别用字符串 `startsWith`），否则同前缀的兄弟目录（`/srv/data2` 之于 `/srv/data`）会被误判为在内部。

## 五、验证纪律

真机验证的价值全在「结论可被第二个人独立复核」，所以：

- **数字以执行者的实际输出为准**，不用「整体看着能用」结案。谁跑的谁报，别人不代报、不复述。
- **命令返回成功 ≠ 结果完成。** 派发类操作（创建会话、起工作树）是异步的：命令立刻返回，那一轮还在跑。要等那一轮真正结束，再读计数或状态。
- **每条判据都要能用接口数字或 `git` 命令客观核对**，不能靠肉眼。能写成「读 X 字段等于 Y」的就别写成「看起来正常」。
- **改完代码先在本地用宿主真实包走一遍**（真实的 `defineTool` 路径、真实的 schema 编译器），别等真机替你发现契约问题——真机一轮的代价是本地一轮的几十倍。
- **工具写成功之后再失败，是会被留下的。** 如果 `execute` 已经把数据写进存储，之后输出校验或 `render` 才报错，调用方看到的是「报错了」，而存储里已经多了一条。所以验证时要**回读状态**确认有没有重复记录，不要只信那一次调用的返回值；设计上也要把「先校验再写」或「失败回滚」当成待补的债，别当成已修好。

## 六、skill 内容也要验

**agent 能干活 ≠ skill 生效。** 提示词里可能恰好有重复的步骤清单，agent 照着做完了，而技能根本没被加载。要看轨迹里的客观痕迹：

- 会话里是否出现**技能目录**注入（`source.kind` 为技能目录类），说明技能进了候选列表；
- 是否有**技能加载**记录（`source.kind` 为技能调用类），说明正文被真正读进去了；
- agent 的后续动作是否引用了 skill 正文里**独有的**方法（只在正文里出现过、提示词里没有的说法）。这一条最能区分「真读了」和「碰巧会做」。

这三条都过了，才能说「skill 生效」。只看到任务完成，只能说明「任务完成了」。

## 七、判断「会话到底跑没跑」

派发型插件最容易把结论搞反：会话明明在跑，却判成「没起来」；明明是自己打断的，却判成「没回执」。这类误判会连续污染好几轮判断，代价比被误判的 bug 本身高。

本节讲的是**取证方法**：去哪里读、读哪些事件。第五节讲的是**验收纪律**：数字以谁的输出为准、什么叫完成。两者不同——先有可信的证据，才谈得上「客观核对」。

### 一手证据只有两类

- `tool/call` 事件：agent 实际调用了什么工具。要数调用次数就数这个事件的 `data.name`，**不要数文本命中**——同一个工具名会出现在系统提示、技能正文和工具定义里，数文本会偏高。
- `turn/end.reason.kind`：这一轮是怎么结束的。异常或被打断会在这里留下痕迹。

### 先确认一个字段有没有人写

判断之前先问：**这个字段谁在写？** 在代码里找不到写入方的字段就不是证据。

典型的假证据有两类。一类是建记录时初始化、之后再无回写的用量字段：它恒为初始值，与真实消耗无关，拿它判「有没有推理」必然判错。另一类是异常中断之后也会出现的收尾事件（会话结束、任务完结之类）：把它们当「正常结束」会把中断后的清理误读成跑完了。结束性质只看一手事件。

还有一类陷阱是**列表类 HTTP 接口在某些宿主版本里整体不可用**。它返回 404 只说明接口不可用，不说明会话不存在、插件没干活。接口不可用时要换一手日志取证，不要下「什么都没发生」的结论。

### 取证顺序

1. 按会话 id 找日志。日志按 cwd 分目录，目录名是 cwd 的转义形式，不必先猜 cwd。
2. 解压并逐行解析，先按事件类型打出时间线。
3. 从 `tool/call` 统计实际工具调用，从 `turn/end.reason.kind` 读结束方式。
4. 需要交叉验证沙箱档位或用量时，再读投影缓存里的 `sandboxMode`、`sessionStats`、`tokenMeasurement`——它是二手投影，不能替代一手事件。

### 别把自己的清理当成产品缺陷

**取证完成、确认 `turn/end` 落定之前，不要清理会话的工作目录。** 会话还在跑就删掉它的工作目录，下一步会以异常中断收尾，于是「它没回执」「它没走完流程」全都是取证动作造成的假象。

### 夹具内容必须与任务相符

验证「agent 会不会留在工作区里干活」时，工作区里必须真有与任务相符的活可干。用只有空壳内容和一次初始提交的仓库去验，agent 发现没有代码可查，去别处找真实源码是合理行为——看起来像「跑出工作区」，实际是夹具与任务不匹配，不是 agent 行为缺陷。

判断「它为什么跑出工作区」之前先排除两件事：工作区里有没有它要的东西；技能正文有没有引导它离开。两件都排除了，才轮得到怀疑 agent。这两条是**定位问题的顺序**，不是给 agent 开脱——环境没配好就不要拿结果当行为结论。

## 八、用例别绑死机器与网络

这条是「环境差异」在用例这一侧的坑：同一条用例，在你这台机器上绿，到 CI 的空环境就红。根因几乎都是同一句——**用例默认了「我机器上现成的机器/网络状态」，而不是把那个状态注进去。**

- **凡「机器上现成有什么」都变成注入参数，别直接读环境。** 判级、解析、取凭据这类逻辑，把会随机器变的东西——`gh` 是否登录（probe）、`GH_TOKEN`/`GITHUB_TOKEN` 在不在（env）、某次网络探测成不成（fetch/verify）——全部收进函数入参，让用例自己决定它们各取什么值。这样同一份代码在「本机有 `gh` 登录」和「CI 什么都没有」两种环境下都能被同一套用例驱动。

- **真实事故**（本仓 GitHub 身份判级那条链上踩的）：某条用例断言「判级会落到 `gh` 登录档」，但它没注入 `probeGhLogin`，而是吃了「我本机恰好 `gh` 已登录」这个默认。CI 里没登录，判级正确地掉到后面的兜底档，断言就翻了——**翻的不是产品，是那条用例把机器状态当成了前提**。修法：把 `probeGhLogin`、`env`、`verifyToken` 都注入，用例里显式写「这一步假设 gh 已登录」，而不是赌跑用例的机器长什么样。

- **活体探测同样要注入。** 令牌档要判「这个 token 现在还活着吗」时，那个探测（发 `GET /user` 一类）要作为参数注入：想验「活」就注入返回成功的桩，想验「死档不亮假绿灯、要往下掉」就注入抛错的桩。别在离线用例里真发网络请求，也别让「CI 发不出去」变成断言失败的原因。

- **断言打到精确字段，别打裸子串。** 同一条链上还揪出过一个：用 `name.includes('token')` 判「这是不是令牌来源」，某个合法来源名里也含这个词，就误判了。判来源就断言到 `source`/`sourceType` 的具体值，别靠「字符串里含不含某词」。

- **一条用例最多假设一种环境。** 想同时覆盖「本机有登录」和「CI 全空」，就写两条、各自注入各自的状态，不要写一条吃默认值、赌机器。

## 九、断言别绑在会漂移的基线上

和 §八同一件事的另一面：§八管「跑用例那一刻的环境」，这节管「断言对照的基线」——它在仓库往前走时自己会变，用例跟着翻红，翻的却不是产品。

- **写死的 key 总数会过期。** 多副本字典每轮都在新增 key，任何 `assert.equal(keyCount, 228)` 都会在下一轮变红——断言把「当前这版的总数」当成了契约。改法：断言**本轮新增的 key 清单逐个存在**（写成固定常量）+ **各副本逐字一致** + **每个 key 的占位符 token 集合不变**，总数交给实际运行去读、不写进文档和断言。
- **`git show HEAD:` 当基线，提交后就翻。** 新用例尚未提交时，拿 HEAD 里的旧文件当期望值可以让它绿；测试一提交，HEAD 变成测试自身，旧基线消失，断言全红（真实事故：7 !== 8、新增 key 变空）。真值只能来自代码里的固定清单、真实 API 读回或注入的夹具；验收用例写下去时就要假设「它和被测代码一起提交」，在提交后的状态下仍全绿才算自足。
- **多副本文案四处一致怎么断言。** 运行时文案常见是内联 zh/en 字典加打包 locale JSON 镜像（zh/en 各一份，共四处，locale 另多一个 `meta`）。同步时要求每处逐字节一致、占位符 token 集合一致、`meta` 不进 UI 字典；验收就按这三条加本轮新增 key 清单写，不写总数。
- **提交闸门是最终验证点。** 本地跑绿不代表提交后绿：rebase、HEAD 前移、key 再增加，都会重算基线。写用例时就以「提交后仍确定性通过」为完成判据。

## 收口前自查

- [ ] 每条宿主契约结论都能指到当前安装里的 `文件:行号`。
- [ ] 宿主包都在 `peerDependencies` 且只写开放下界；需要时标 `optional`。
- [ ] 工具输出没有 `undefined` 成员；可选字段是「键不存在」。
- [ ] 每个 `render` 都返回内容块数组，不是字符串。
- [ ] 技能注册带了非空 `source`。
- [ ] 输出 schema 的 object 节点都显式写了 `additionalProperties`。
- [ ] 有一个可被外部读到的状态字段，能证明「工具/技能到底注册上没有」。
- [ ] 可选服务一律用 `ctx.get(name)` 探测，没有用 `typeof ctx.xxx` 直接读属性。
- [ ] 至少一条用例用真 Cordis `Context` 构造，能复现「未声明依赖读服务属性会抛」。
- [ ] 代码里没有任何本机绝对路径；路径从环境变量派生、惰性求值、`~` 用 `homedir()` 展开且先展开后 `resolve`。
- [ ] 每条验收判据都写成了可客观核对的数字或命令输出。
- [ ] 异步操作是等它跑完再读的计数，不是命令一返回就下的结论。
- [ ] 技能生效性是从轨迹痕迹核过的，不是从「任务做完了」推断的。
- [ ] 判断会话状态时用的是一手事件（`tool/call`、`turn/end.reason.kind`），没有拿用量字段、收尾事件或可能不可用的列表接口当证据。
- [ ] 当证据用的字段先在代码里确认过「谁写它」；工具调用次数数的是事件，不是文本命中。
- [ ] 取证完成、`turn/end` 落定后才清理工作目录；夹具仓库里有与任务相符的内容。
- [ ] 每条验证用例的机器/网络状态（`gh` 登录、env token、网络可达、活体探测）都是注入的入参，用例没在吃「我机器上恰好有 X」的默认；换到 CI 空环境仍确定性通过。
- [ ] 来源/判级这类断言打到具体字段值，没用 `includes` 之类裸子串去猜。
- [ ] 断言没写死会随迭代增长的 key 总数，改用固定新增清单 + 跨副本逐字一致 + 占位符集合。
- [ ] 验收基线不是 `git show HEAD:` 的旧文件，而是代码常量、真实 API 读回或注入夹具；测试提交后仍全绿。
