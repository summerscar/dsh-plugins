# 在真机上验证一个 DSH 插件

插件在单元测试里全绿、在真机上却「装上了但用不了」，是这类开发最常见也最贵的故障。原因不是逻辑写错，而是**宿主契约没满足**——契约不满足时宿主往往只打一行日志、把功能悄悄摘掉，命令和 HTTP 接口照常工作，从外部看就像一切正常。

这个 skill 教的是**怎么把「能用」变成一个可客观读到的数字**。它不提供命令清单：装什么、跑什么、用什么包管理器，一律按目标仓库自己的 `AGENTS.md` / `CONTRIBUTING` 决定。

## 一、先读宿主源码，别读文档

契约写在宿主包里，不在任何介绍文章里。宿主的安装目录下有 `node_modules/@deepseek-ai/dsh-*` 这些包，它们就是权威：

- `dsh-tools`：工具定义、schema 子集、执行流水线（参数校验 → `execute` → 返回值快照与 schema 校验 → `render` → 渲染结果快照 → 发布结果）。
- `dsh-skill`：技能注册表、`register()` / `get()` 的字段校验。
- `dsh-llm`：内容块（`ContentBlock`）类型与消费方，很多「下游崩」的根因在这里。
- `dsh-app-boot`（或同级的启动/加载器包）：模块解析、peer 注入。

**每条结论都要能指到 `文件:行号`**，写进报告或注释。凭印象写下的契约，下一代宿主就会打你的脸。契约本身也会变，所以 skill、注释里写的是「当时实测到的形态」，不是合同——动手前重新读一遍当前安装的那份。

## 二、工具过宿主，要过四道关

模型可见工具（`ctx.tools.register(defineTool(...))`）任何一道不过，就是整条链断掉。

### 1. 宿主包必须写进 `peerDependencies`

宿主的 loader 只在**插件自己的 `package.json` 声明过这个 peer** 时才会注入它。启动器里的 `readPeerNames(dir)` 读的就是被解析目录的 `package.json` 的 `peerDependencies` 键集合，没声明就构造不出注入路由，于是 `import '@deepseek-ai/dsh-tools'` 直接 `MODULE_NOT_FOUND`。

- 版本范围只写**开放下界**：写上界会让 loader 命中 profile 里装着的旧拷贝，版本检查失败并把插件停用。
- 宿主内置的包放进 `peerDependencies`，并在 `peerDependenciesMeta` 标 `optional: true`，避免自动装 peer 时在本地装一份物理副本。
- 源码里用动态 `import()` 并留降级路径：拿到宿主包再注册工具，拿不到就退化成「只有 HTTP/UI，没有工具」并**把这件事暴露成状态**（见第三节）。
- 判断「宿主到底有没有内置某个包」，别猜：从插件目录 `createRequire` 试一次解析。解析不到就说明只能靠注入，为它再押一个 peer 未必划算。

### 2. 工具返回值必须是 lossless JSON

流水线在 `execute` 之后会快照返回值，`undefined` 成员、函数、`Map`、类实例、稀疏数组都让快照失败，整次调用报错。典型写法错误是「可选字段赋 `undefined`」：

```js
// 坏：warning 为空时整次调用失败
return { id, warning: maybeWarning }
// 好：没有就不带这个键
return { id, ...(maybeWarning ? { warning: maybeWarning } : {}) }
```

注意 `null` 也不一定是替代品——如果 schema 里该字段是 `string`，`null` 会过不了输出 schema 校验。**「键不存在」才是缺省的正确表达。**

同一个位置还有一条容易漏的：**输出 schema 里的 object 节点必须显式写 `additionalProperties: true|false`**，宿主不接受「没写」这种开放缺省，编译 schema 时就报错。schema 只支持一个很小的关键字子集（`type` / `oneOf` / `properties` / `required` / `additionalProperties` / `items` / `enum` / `const` 加注释字段），写之前先看 `dsh-tools` 支持清单，别按 JSON Schema 的完整印象写。

### 3. `output.render` 必须返回 `ContentBlock[]`

`render(args, value)` 的返回类型是内容块数组，例如 `[{ type: 'text', text }]`。返回一个裸字符串**能通过快照**（字符串是合法 JSON），但下游消费内容块的地方会直接崩：判断是否含图片的 `contentHasImage()` 做的就是 `content.some(...)`，字符串没有 `.some`，于是**这个工具的每一次调用都失败**。

一个包内共用的 `textBlock(text)` 小助手能一次性堵住这类手误，值得写。

### 4. `skills.register` 必须自己传 `source`

宿主 `register()` 只给 `provider` 和 `invocation` 兜默认值，**`source` 不兜**。注册当下不校验它，所以注册「成功」了；等到真正加载技能正文时，定义校验会以 `loaded skill "<name>" source must be a string` 失败——错误信息里的 `loaded` 就是线索：问题在读取路径，不在注册路径。

随包分发的技能，统一用一个格式的来源标识（例如 `<包名>:<技能名>`），不要留空字符串。

注意这条和上面 `additionalProperties` 一样，属于**「注册时不报、读取时才炸」**的一类：判断某个字段到底必不必填，看 `register()` 的默认值合并逻辑，也看 `get()` 走的定义校验，两处都要读，别只读一处就下结论。

## 三、静默降级是最大的坑

宿主的常态是「优雅降级」：没有 `tools` 服务就不注册工具，`import` 失败就吞掉异常打一行 `console.error`。于是真机表现是——**命令说成功了，agent 手里却一个工具都没有**。这种故障最贵，因为它不报错。

对策是把状态变成**可被外部读到的字段**：

- 插件暴露一个状态接口，里面带类似 `toolsRegistered: true|false` 的布尔值，语义是「这批工具要么全注册上、要么一个都没上」。
- 注册是**全有或全无**：中途失败要把已注册的撤掉，再翻状态位。只注册一半却报「失败」，比一个都没注册更难查。
- 验证时**只认这个字段，不采信 agent 的自述**。agent 说「我调用了工具」可能只是在描述它以为发生过的事。

同理，注册技能的条数、HTTP 路由是否挂上，都应该有一个可读的计数或布尔，而不是只能从日志里猜。

## 四、路径判断必须走环境变量

开源产物里**不能出现本机绝对路径**。数据根这类宿主既有概念，要从宿主自己的环境变量派生（如 `DSH_HOME`），其余路径用自己的配置项 + 中性缺省（临时目录之类）。

几条踩过的细节：

- **要写成惰性函数，不要写成模块级常量。** 模块级常量在 `import` 那一刻就把环境冻住了：同一进程里改环境变量测不出来，测试和消费者也换不了环境。每次调用现取环境才对。
- **`~` 要自己展开，用 `homedir()`，不要读 `process.env.HOME`。** 而且展开必须在 `resolve()` **之前**——`resolve('~/x')` 会把它当相对路径，于是数据根跟着进程的当前工作目录漂移。这个 bug 只在从别的目录启动时才显形，非常隐蔽。
- **空白字符串按「未设置」处理**（`trim()` 后判空），不要当成一个叫空白的路径。
- 缺省值要和宿主的语义一致。宿主未设置时回落 `~/.dsh`，插件就不该回落某个具体机器上的目录。
- 路径包含关系判断要**分隔符安全**（用 `relative()` 判，别用字符串 `startsWith`），否则同前缀的兄弟目录（`/srv/data2` 之于 `/srv/data`）会被误判为在内部。

## 五、验证纪律

真机验证的价值全在「结论可被第二个人独立复核」，所以：

- **数字以执行者的实际输出为准**，不用「整体看着能用」结案。谁跑的谁报，别人不代报、不复述。
- **命令返回成功 ≠ 结果完成。** 派发类操作（创建会话、起工作树）是异步的：命令立刻返回，那一轮还在跑。要等那一轮真正结束，再读计数或状态。
- **每条判据都要能用接口数字或 `git` 命令客观核对**，不能靠肉眼。能写成「读 X 字段等于 Y」的就别写成「看起来正常」。
- **改完代码先在本地用宿主真实包走一遍**（真实的 `defineTool` 路径、真实的 schema 编译器），别等真机替你发现契约问题——真机一轮的代价是本地一轮的几十倍。
- **工具写成功之后再失败，是会被留下的。** 如果 `execute` 已经把数据写进存储，之后输出校验或 `render` 才报错，调用方看到的是「报错了」，而存储里已经多了一条。所以验证时要**回读状态**确认有没有重复记录，不要只信那一次调用的返回值；设计上也要把「先校验再写」或「失败回滚」当成待补的债，别当成已修好。

## 六、skill 内容也要验

**agent 能干活 ≠ skill 生效。** 提示词里可能恰好有重复的步骤清单，agent 照着做完了，而技能根本没被加载。要看轨迹里的客观痕迹：

- 会话里是否出现**技能目录**注入（`source.kind` 为技能目录类），说明技能进了候选列表；
- 是否有**技能加载**记录（`source.kind` 为技能调用类），说明正文被真正读进去了；
- agent 的后续动作是否引用了 skill 正文里**独有的**方法（只在正文里出现过、提示词里没有的说法）。这一条最能区分「真读了」和「碰巧会做」。

这三条都过了，才能说「skill 生效」。只看到任务完成，只能说明「任务完成了」。

## 收口前自查

- [ ] 每条宿主契约结论都能指到当前安装里的 `文件:行号`。
- [ ] 宿主包都在 `peerDependencies` 且只写开放下界；需要时标 `optional`。
- [ ] 工具输出没有 `undefined` 成员；可选字段是「键不存在」。
- [ ] 每个 `render` 都返回内容块数组，不是字符串。
- [ ] 技能注册带了非空 `source`。
- [ ] 输出 schema 的 object 节点都显式写了 `additionalProperties`。
- [ ] 有一个可被外部读到的状态字段，能证明「工具/技能到底注册上没有」。
- [ ] 代码里没有任何本机绝对路径；路径从环境变量派生、惰性求值、`~` 用 `homedir()` 展开且先展开后 `resolve`。
- [ ] 每条验收判据都写成了可客观核对的数字或命令输出。
- [ ] 异步操作是等它跑完再读的计数，不是命令一返回就下的结论。
- [ ] 技能生效性是从轨迹痕迹核过的，不是从「任务做完了」推断的。
