# 派发型 agent 会话的宿主机制

这类功能的共性：宿主在运行期替 agent 创建会话，把任务上下文喂进去，让它在受控沙箱里干活，最后由工具写盘。四个环节各自有宿主契约，契约不满足时宿主往往不报错、只是悄悄降级——和「装了插件但用不了」同一类病，但发生在会话层而非工具层。

## 一、注入上下文：选对通道

宿主给会话喂文字有两条通道，语义不同，选错通道不会报错、只会在后面某个环节暴露：

- **指令 / 规则 / 当前卡的操作说明** → `systemPrompt.section()`。它是 system prompt 的一部分，和角色设定、工作规则同源。正文用 `() => value` 实时求值：阶段变了、字段更新了，下一次 assembly 自动换内容，不需要重建会话。
- **随时间 / 状态刷新的动态事实**（比如当前时刻、工作区的 git 状态） → `systemPrompt.context()`。它物化为一条 user 角色的快照，有自己的排序（`order`）与必填标记（`required`），在 `refreshContext` 时刷新。

判断口径：**这段文字是「这一轮该怎么做」就用 section，是「现在世界是什么样」就用 context**。把跨阶段推进规则写进 context 会失去和角色规则的优先级语义；把易过期事实写进 section 会撑大提示词本体。

**误读陷阱**：阶段类文案（"本阶段的最后一步是 X"）很容易被模型读成「整个会话的终点」。写阶段指引时，把「阶段终点」和「会话终点」显式分开：可推进阶段（triage/plan/build/review）在同一会话内连续完成，只有人工门（plan-review/done/canceled）才是停手态。

## 二、沙箱：钉死 + 回读，不靠时序

给自动创建的会话定权限档，宿主有三个坑：

1. **档位来源比你想的高**。宿主可能在全局事件（会话创建钩子）里给每个新会话钉一个 profile 默认档，这个动作比你的 setup 逻辑优先级高。只在你自己的 setup 里设模式，会被后来的钩子覆盖成全权。
2. **正确姿势：写进构造参数（seed），不抢跑**。宿主创建会话的执行顺序是「先写初始事件 → 再跑 setup → 最后通知」。把 `sandbox/mode` 作为初始事件传入，后续钩子看到已存在就不覆盖——不依赖时序、宿主改顺序也不失效。
3. **建完必须回读投影校验**。写了事件 ≠ 生效。建完会话后读宿主的投影（sandboxMode 之类），与期望不符就处置会话并走失败回滚，别假设。

权限上限要封顶：自动派发的会话即使项目配了更高档，也只放行到工作区可写级——自动链路不该拿全权。

## 三、写操作的回执：先预检再落库

宿主工具的流水线是「execute（写入已发生）→ 快照 → 无损校验 → 渲染」。如果在校验阶段才失败，**写已经落库、回执却丢了**——表现为「操作报错了，但状态库里已经有这条记录」。

修法（按宿主同款规则做预检）：在落库之前，对即将写入的值完整跑一遍宿主的校验链——无损性 → schema → 渲染 → 渲染结果无损。全部通过才允许写；任何一步失败就抛**原始错误**（不包装、不吞），并走该操作自身的失败回滚。

判断口径：凡「写入动作 + 宿主会校验/渲染这个值」的工具，都该有这道预检。预检的校验实现优先复用宿主公开的校验函数（注入进来），避免两份同语义实现日后漂移；复用不了就隔离在一个模块里，将来宿主规则变化只改一处。

## 四、档位与幂等：机器只走它被授权的边

自动推进的状态机要守死两条：

- **actor 语义分层**：自动规则（autoRule）、同步规则（syncRule）、人工（human）各走各的边。机器只允许走被授权的边（比如「计划 → 建造」），且目标状态由远端事实推导、调用方指定不进去——调用方传目标列/actor 的参数一律忽略。
- **急停必须立即生效且不补跑**：全局暂停、项目暂停、单卡接管都要挡住下一次自动动作；暂停期间跳过的卡，恢复后不补跑、下一轮重新判断。重复 tick 幂等（已推进过的不再推）。

## 五、验证纪律（承接 live-verification）

- 判断会话真实状态只认 `tool/call` 事件与 `turn/end.reason.kind`；卡片字段、API 返回值、崩溃后的收尾事件都不算。
- 夹具仓库必须含与任务相符的源码，空壳仓会造出「agent 不守工作区/不回执」的假象。
- 取证清理前等 `turn/end` 落定。

这些真机验证的执行细节见 `dsh-plugin-live-verification` 技能；本 skill 只管「机制为什么这样设计」。
