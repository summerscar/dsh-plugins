# dsh-factory roadmap

> Status: describes behavior as implemented, not a schedule; every phase listed here is complete. This document is for anyone taking over the project: after reading it you should be able to judge on your own what it can do today, what comes next, and why it was decided that way.
> The **reasons** behind each design choice live here, so they do not have to be argued again. For implementation details read the source; for how to run things read the repository's own `AGENTS.md` and per-directory conventions.

## 1. What this plugin is for

Turn one piece of work (a GitHub issue) into a reviewable pull request, with every step carried out by its own agent session, and a person only approving at the gates that matter.

Three points that are not negotiable:

1. **One card = one dedicated session + one dedicated working tree.** Cards never share a working directory, and never share dependencies.
2. **commit / push / opening a pull request is always approved by a person.** The plugin may prepare everything automatically, but it never pushes changes out by itself.
3. **Multiple projects are first-class.** Each project has its own root path, one board, cards and configuration, and they do not interfere with each other.

The long-term goal is "discover issues on a schedule → analyse → develop automatically → deliver a draft pull request", but **merging always stays with a person**.

## 2. What it can do today

### 2.1 Data and boards

- **One board per project: project → board → card.** Creating a project writes its single board in the same transaction; a repeated board creation returns that board instead of adding another, so the boards listing never shows more than one active board per project. Legacy multi-board state is converged when it loads, without a schema bump: the first *active* board is kept, cards belonging to the other boards are moved to it, every project's `intakeBoardId` is repointed to it (including one already pointing at an archived board), and the extra boards are marked `archived` and kept in state. No card and no board is deleted, and repeating the load is a no-op. Manual intake through an old archived board id is refused with 400.
- The schema version stays at `1`; loading state with a different version throws. Data repair for this change therefore goes through archival in place rather than a schema upgrade.
- A card's lifecycle has 8 statuses: `inbox` / `triage` / `plan` / `plan-review` / `build` / `review` / `done` / `canceled`.
- **A card can be cancelled (soft delete).** Every non-terminal card (anything other than `done`/`canceled`) has a "Cancel card" button at the end of its action area; it calls `POST /cards/:id/transition {to:'canceled',actor:'human'}` through the existing state machine with no backend change, asks no confirmation, shows a toast on success and the server's original message on failure. Cancelling changes state rather than deleting data: the card stays in the store and its `source` keeps its place, so an auto-imported card is not recreated by the next intake; body, history and audit remain, automatic dispatch and approval stop, and the worktree / branch are untouched. The UI surfaces it through a trailing "Canceled · N" disclosure strip: expanding it shows each cancelled card's title and body summary (rendered with `renderCard`, read-only because no action button applies at the terminal status), without taking a sixth board column; there is no per-card hard delete.
- **The task-card count excludes canceled and keeps done.** The top-right "Task cards" stat uses `boardCards.length - canceledCards.length`, and the `cardCounts` loop shared by the sidebar and tab strip skips `status==='canceled'`, so both displays agree; `done` still counts and stays in the "Done" column. The totals conserve: task cards (non-cancelled) + footer canceled = all cards. "Active sessions" and "Free slots" are unaffected.
- Every transition records who made it (person / agent / automatic rule) and is auditable globally.
- The inbox is a data status shown separately in the interface; it does not take a board column.
- **State is persisted in SQLite**, using the host runtime's bundled SQLite (`node:sqlite`, imported statically). The whole state — projects, boards, cards, events, settings and a schema version — lives as one JSON document in a single row; the in-memory model and its public methods are unchanged, so callers do not see the engine change, and data survives a plugin reload.
- The default database file is `<DSH home>/dsh-factory/factory.sqlite`. DSH home is always resolved through the host package `@deepseek-ai/dsh-home-paths` (`resolveDshHome`) — never a hand-written fallback — so the location follows the host's own config / `DSH_HOME` / default resolution. `config.dataDir` or `DSH_FACTORY_DATA_DIR` overrides the directory. The host package is a peer dependency.

### 2.2 Dispatch and working trees

- Dispatching a card creates a **git worktree** on branch `factory/<cardId>`, and the session's working directory is that worktree.
- **Worktree isolation is mandatory and has no off switch**: every project and every autonomy level works inside a worktree. The reason is that editing directly in the project root pushes the wrong branch, drags in uncommitted changes, and makes it impossible to tell which changes the approval gate is approving.
- After the worktree is created, a project may run its own preparation steps:
  - `copyFiles`: copy locally ignored files from the project root (such as environment files) into the worktree;
  - `postCreate`: run a preparation command the user supplied, inside the worktree.
  - Neither ships a default: what to install and what to verify is decided by the target repository's own conventions. If either step fails, the whole dispatch rolls back (the worktree and branch are removed and the card stays in the inbox).
- **A single global "worktrees root" setting** decides where new worktrees are created. It lives in the **global** pane of the settings drawer (under "Paths & concurrency"), not on the project page. Leaving it empty uses the default `~/dsh-factory-worktrees` (resolved from the user's home): the input's placeholder shows that default and a "currently in effect" line shows the resolved absolute path. It affects only worktrees created from then on — existing projects and cards already in flight are untouched. A rejected value surfaces the backend's original error verbatim. Under the root, each project gets a directory named from a slug of the project name plus a short prefix of its id (so renaming cannot break the path and same-named projects stay distinct), with each card's worktree nested beneath it.
- **Worktree paths are kept out of the data root by one shared gate.** The root may sit outside the data root normally; the only in-root exception is the single exact `<home>/dsh-factory-worktrees` subtree, for layouts where HOME itself lives under the data root. Session storage, caches, other projects' state and a same-named directory elsewhere stay forbidden. Containment is resolved live on every call (`resolveDataRoot()` / `homedir()`, never cached), and `assertWorktreeRoot`, `worktreePathFor` and `createWorktree` all pass through the same `isAllowedWorktreePath` check. An explicit `DSH_FACTORY_WORKTREE_ROOT` override does not inherit the exception. On machines whose HOME is outside the data root, behaviour is unchanged.

### 2.3 Stage continuation (three-level fallback)

A card passes through several stages; each needs a new agent session, but must reuse the same worktree and branch. Continuation falls back through three levels, recording each step instead of doing it silently:

1. **The session is still live** → append to the same session (cheapest);
2. **The session ended but its history is on disk** → resume from the persisted session, with full context;
3. **The history is unusable** → create a new session, inject a history digest, and record the fallback on the card.

Failure handling: a failed continuation only releases the claim. It does not change the card's status, does not delete the worktree, and can be retried.

### 2.4 Circuit breaker

A card that fails dispatch repeatedly up to the threshold (currently 3) is marked stalled and stops retrying automatically, waiting for a person.

### 2.5 Approval gates

- **Commit** and **push branch and create PR** are two separate human actions; without approval there is no git write at all.
- Every pull request is opened as a **draft** at all autonomy levels, including `manual`; automatic modes may reach a draft pull request, but **never merge**, never mark done, and never escalate permissions on their own.
- Pushing to a protected branch is refused, an empty diff is refused, and it never force-pushes.

### 2.6 Project creation assistant

- A read-only analysis tool: it reports objective facts about the target repository (root files, directories, ignore rules, manifest files, the declared package manager) and **returns no conclusion about which command to run**.
- A creation tool: registers a project directly. Creating one is local, reversible configuration — it performs no git write. It **drops any `copyFiles` entry the git index already tracks** — a tracked file is already in a fresh worktree, so copying it is redundant; this is a deterministic guard, not a matter of model judgement.
- **One-shot GitHub binding at project creation.** `createProject` reads the local git `origin` once with read-only commands and, only for a github.com HTTPS or SSH URL, parses `owner/repo` into `issueRepo` in the same transaction that creates the default board and points `intakeBoardId` at it. An explicitly supplied `issueRepo` wins and skips detection. A missing remote, a non-GitHub URL, a non-git root, or several origin URLs never block creation — each records a `bindingReason` code that the identity card explains in plain words. **Detection is user-initiated and happens only at creation; the engine at runtime never guesses a repository and never reads a remote (see the `manual` note in P2), and detection never backfills historical projects.** In project settings the binding can be rebound or cleared by hand: the value must be `owner/repo`, and leaving it empty clears the binding.
- The `/factory add [path]` command is only a **trigger**: it hands the intent to the agent, and the `factory-add-project` skill guides the agent to analyse the repository, propose a configuration, and then create the project. Without a path it uses the current session's working directory.
- A project root **may** live inside the data root (some of the user's repositories do): it is registered with a warning, but it is **never** used as a session cwd, and its worktree is forced outside. Verified on a real machine (V2b).
- `GET /api/dsh-factory/status` exposes `toolsRegistered`: tool registration used to degrade silently (the command and the API both succeeded while the agent had no tools to call), and this is now an objectively readable signal.

### 2.7 Skills

Seven: six phase skills (triage / plan / build / self-review / review / rereview) plus one project-add skill. The phase skills line up one-to-one with the transitions an agent is allowed to make in the status machine.

### 2.8 Autonomy levels

There are three semantic levels, stored and displayed as `manual` / `you-approve` / `machine-approve`; new projects start at `manual`. The old `L0` / `L1` / `L2` ids and the `autoStart` / `autoApprove` switches are gone from the UI, storage, engine and tests; the only switch is `autoDispatch`, and it belongs to `you-approve` alone. There is no allowlist of repositories or cards.

- `manual` does nothing: no discovery, no dispatch, no approval.
- `you-approve` discovers issues; its single `autoDispatch` switch decides the rest. On, the engine takes the `inbox -> triage` edge and a card stops at `plan-review` for a person; off, the engine only creates inbox cards.
- `machine-approve` takes one more automatic edge — `plan-review -> build` — and checks no switch at all: the level is the single source of truth. The machine approves the plan on the card's behalf, then continues that card's session so `build` actually runs; approving alone would strand the card in `build` with no agent. It uses the same `autoRule` actor and the same `assertTransition` state gate as every other move, so it cannot reach a state the gate does not allow. The boundary is deliberate: the machine **only approves plans and resumes their session**. Arming the delivery authorization (commit, push, opening a pull request) still belongs to a person, and the machine never touches git or creates a pull request. This is narrower than "fully automatic to a draft PR" — the machine does not arm or deliver.

**Migration of old archives.** The store's schema version moved from 1 to 2, and an old archive is rewritten once when the store loads (a load never rejects an old or corrupt archive): `L0` → `manual`; `L1` with `autoStart` on or off → `you-approve` with `autoDispatch` on or off; `L2` with both switches on → `machine-approve`; `L2` with `autoStart` on and `autoApprove` off → `you-approve` with the switch on; `L2` with `autoStart` off → `you-approve` with the switch off; anything missing or invalid → `manual`. The old field names are dropped from the persisted state.

**The audit tier is the level.** Every intake, dispatch and approval record carries the project's level as its tier — `machine-approve` events under `tier=machine-approve`, `you-approve` events under `tier=you-approve` — so the records of one level always filter to one tier.

Approvals share the same concurrency budget as dispatch: a per-project and a global ceiling bound live sessions, and a plan is approved only if a slot is free. Reusing a still-live session (followup) opens no new session and consumes no slot; only a `resume`/fresh fallback — which genuinely starts a session — is charged against the budget. When no slot is free the approval itself is held, not just the continuation: the card stays in `plan-review` (recorded as held for capacity) and a later tick retries, so it is never approved into a `build` with no agent to run it. Liveness is checked both at tick start and again at the decision point, so a session that dies mid-tick cannot slip through slot-free and open a session over the cap.

`pause` and per-card `takeover` take effect immediately for approvals too: a paused project or a taken-over card is not auto-approved, and cards skipped during a pause are not made up for when it resumes. Repeated ticks are idempotent, and this automatic edge has no path to `done` or `canceled`.

### 2.9 Whole-page view, configuration drawer, copy and narrow-screen board

- **The view is designed as a whole page.** A sticky in-page header sits at the top of the plugin (56px tall); a project sidebar and a top tab strip are two presentations of the same project selection, switched by a **View** control (sidebar / tabs). The sidebar is the default, and the choice is remembered across reloads in local storage — no backend field and no schema change. Both navigation forms show each project's level badge (`manual` / `you-approve` / `machine-approve`), card count and paused marker, all derived from data already loaded for the board. On wide screens the sidebar is fixed beside the board; on narrow screens it becomes a slide-in drawer with a scrim, while tabs stay a horizontal strip. The board itself keeps real vertical space (min-height 440px), and the global pane puts the GitHub connection group first.
- **Actions give centred, page-root feedback.** Switching into `machine-approve` from another level first opens a confirmation that saves on confirm and leaves the stored level and switch untouched on cancel; switching away from it asks nothing. Deleting a project uses a typed, centred confirmation. To avoid a fixed overlay being trapped by the transformed drawer, these dialogs render at the page root. Save results and card actions (for example takeover) surface an auto-dismissing toast, with success and failure visually distinct.
- **The settings drawer opens project-first.** Its scope starts at `auto` and resolves to the current project when one is selected, otherwise to global; clicking a tab pins an explicit scope for that page session only, and a reload starts over at `auto`. The project pane carries a "Global settings ›" link and the drawer heading follows the active pane. Project pause/resume calls the project endpoints; the engine pause/resume switch exists only on the global pane. The project pane keeps the identity card visible and merges autonomy with pause into one block, with the worktree setup, concurrency and danger blocks around it; the global pane groups GitHub connection, paths & concurrency, and engine.
- **Runtime copy has one source.** Every `t()` string comes from the inline zh/en dictionaries registered with the locale service. The packaged locale JSON files carry the host-facing `meta` and mirror the same UI key set: across all four sources (inline zh/en and locale zh/en) overlapping keys are byte-identical and each key's placeholder token set matches, and only the locale files add `meta` (which never enters the UI dictionary). The total number of UI keys grows with each iteration and is not frozen in documentation — self-contained assertions check it at runtime. Product terms — GitHub Token, gh CLI, GitHub OAuth App, Client ID, worktree, commit, PR — are written verbatim in both languages. The old generic "account unknown" wording is no longer shown for a connected identity: when the account cannot be resolved the card falls back to the source label.
- **Narrow-screen board.** At the plugin's 760px breakpoint the board becomes a horizontal scroll-snap strip: columns take 84% of the viewport width, column heads are sticky, the board is capped at 56% of the viewport height, and a stage indicator shows the current column out of five, computed from the rendered column's real width. QA's real-machine re-check at 390px found one column per screen with snapping intact and no page-level horizontal overflow; the rendered outer column width is about 348px because the column is `content-box` with padding, a recorded non-blocking discrepancy. Wide viewports — including a narrow host content column — keep ordinary horizontal scrolling with every column reachable.

### 2.10 Card body (task description)

- **A card can be created with a body.** The new-card modal at the page root has a "Task description" textarea next to the title (its placeholder spells out background / goal / acceptance criteria); `POST /cards` carries a `body` field. The body may be empty — creating is disabled on a missing title or board, not on a missing body.
- **The card-face summary is read-only plain text.** The client strips the body to plain text (removing Markdown/HTML marks, reducing links and images to their text, collapsing blank lines), clamps to two lines with a 240-code-point cutoff, and exposes up to 2000 code points in the hover `title`; an empty body renders no summary node at all. The summary cannot be expanded or clicked; the full content goes to the session instead.
- **The body is injected ahead of the skill instructions.** On dispatch, the system prompt injects a separate block before the phase skill body: untrusted-data notice → snapshot notice for auto cards → body → truncation hint. The notice tells the agent to ignore text in the body that tries to change the task, loosen criteria or issue commands; it sits at the head of `sectionText`, before the card fields and the skill body. A manually created card has no source, so its body is injected in full with no snapshot notice and no truncation hint; only a card with a real source (non-empty `source` other than `manual`) is truncated past 3000 code points, with a hint to re-read the GitHub issue. Truncation cuts on code points and never splits a surrogate pair.
- **Prompt notices share the UI copy source.** These notices and hints are read from the packaged locale dictionaries, never kept as a second literal in `session-context.js`; the locale is resolved from the host context and falls back to zh (the long-standing default).

### 2.11 Per-card takeover and return

- **Takeover takes one card out of the engine.** `POST /cards/:id/takeover` sets `takenOver=true`, appends a `takeover` history entry and a `taken-over` audit event. The board card and the inbox list card use one shared "Taken over" badge (one component, one condition); takeover does not interrupt a running session — it only makes later ticks skip the card and stops automatic approval of it.
- **Return only flips one flag.** `POST /cards/:id/release` sets `takenOver` back to `false`, appends a `returned-to-engine` history entry and an audit event with `decision=returned-to-engine`, and touches none of `sessionId`, `pendingDispatch` or the worktree — those belong to the running session, which the engine already skips. Return does not dispatch immediately; the next tick picks the card up under the normal concurrency gate.
- **Idempotent, with no second confirmation.** Calling `POST /cards/:id/release` on a card that is not taken over is a silent no-op — no new history or audit entry. Return is reversible, so the UI shows no confirmation dialog; `busy` is the only guard against a double submit. With a live session or dispatch lock, the success toast appends a second line telling the user that the session continues and the engine will not dispatch again.
- **Return is not the dispatch lock.** `/release` means "a person gives the card back to the engine"; it is a different route from `releaseClaim`, which frees a concurrency slot. Do not confuse them.

## 3. Decisions already settled — no need to reopen them

| Decision | Reason |
|---|---|
| Worktree isolation is mandatory, no off switch | Turning it off means working directly in the project root: wrong branch, uncommitted changes dragged in, and no way to bound which changes the approval gate covers |
| Isolation uses git worktrees, not separate clones | The two are equivalent on "independent dependencies, local files must be copied"; worktrees are created in seconds, the remote is correct by construction, and they do not pile up extra workspaces in the sidebar |
| No attempt at a real container sandbox | The host environment has no container capability, so the isolation on offer is "restrict where writes may land"; we do not pretend it is strong isolation |
| Worktree paths outside the data root, with one narrow home-subtree exception | A worktree landing in session storage, caches or another project's state would corrupt unrelated data; the only tolerated in-root path is the exact `<home>/dsh-factory-worktrees` subtree, resolved live per call and shared by all three boundary checks |
| A single global "worktrees root" setting, empty means the HOME-resolved default | One setting is easier to reason about than per-project roots; the default is expressed via `homedir()`, never a machine-specific absolute path |
| A new session per stage with a history digest, rather than one session throughout | Review must be independent: reviewing your own work breaks injection defence and review discipline |
| SQLite instead of a single JSON file | The whole state in one row keeps the in-memory model and every caller unchanged while giving a real database file; a reload reads the data back intact |
| Resolve DSH home only through the host package | `@deepseek-ai/dsh-home-paths` is the single source of truth for config / `DSH_HOME` / default — a hand-written fallback would drift from the host layout |
| Plan approval and delivery authorization stay with a person by default | The default keeps every gate human; `machine-approve` can delegate **only plan approval** through the explicit per-project level choice, never delivery |
| Only `machine-approve` may auto-approve a plan, and only when that level is chosen | New projects default to `manual`, no allowlist, no switch read; the machine approves `plan-review -> build` via `autoRule` through the same state gate, then stops. Arming delivery, git writes and merge stay human |
| One board per project, converged by archival rather than by deletion | A board is the project's intake surface, not a user-managed grouping; archival keeps historical cards and intake targets resolvable while the API still exposes one active board per project, and it avoids a schema-version bump |
| Settings drawer defaults to the current project | Someone opening settings from a project almost always wants that project's settings; global stays reachable through the tab and the project-page link |
| Inline dictionaries are the runtime copy source; locale JSON mirrors them | One place to change a string, with a key-set parity check so the two copies cannot silently drift |
| Product names are written verbatim in both languages | Replacing GitHub Token / gh CLI / GitHub OAuth App / Client ID with generic wording made the configuration unintelligible |
| Card bodies are marked as untrusted data and injected before the skill | A body comes from an issue or a person and cannot be trusted; placing it before the skill instructions, with an explicit directive to ignore attempts to change the task or loosen criteria, is what contains prompt injection |
| Only cards with a real source are truncated at 3000 code points with a re-read hint; hand-written cards are injected in full | A hand-written card's body is the only task content there is — truncating it leaves no full text to read back; only source-backed cards can be re-read from the issue |
| Return clears only `takenOver`, leaves the session / lock / worktree alone, and dispatches on the next tick | Those fields belong to a running session; clearing them would double-dispatch or lose the workspace. Deferring one tick lets the engine pick the card up under its own concurrency gate |
| Return is idempotent and needs no confirmation | Repeating a return is a meaningless write; the operation is reversible and lighter than takeover, so a confirmation only interrupts |
| Cancelling a card is a soft delete (move to `canceled`), not a physical delete; `source` keeps its place to prevent recreation | Intake deduplicates on existing cards' `source` and ignores status; hard-deleting an auto card removes its source so the next round recreates it as a fresh issue, and breaks the history / audit chain. Keeping the card and changing its state both exits the pipeline and avoids recreation, using backend and rendering that already exist |

## 4. What comes next (in priority order)

### P1 — End-to-end verification on a real machine (**done**, 2026-11-15)

The full `/factory add` chain — command → agent → skill → tools → the project appears on the board — **has been run on a real machine and converged in six rounds.**

- Acceptance (final form, seven groups): **V0** tools are registered (read `toolsRegistered` from `GET /api/dsh-factory/status`, never the agent's own account); **V1** bare `add` (the session cwd must be a real git root **outside** the data root — an environment constraint, not a plugin policy); **V2a** `add` with a path outside the data root; **V2b** `add` with a repository **inside** the data root (registered + a `warning` + the worktree lands outside the data root); **V3** the agent really called the tools **and the calls succeeded** (not the command creating the project itself, and not the agent falling back to something else after an error); **V4** the proposal is justified, every `copyFiles` entry is untracked, and no command is baked into the plugin; **V5** the project appears on the board and the repository files survive deletion.
- Evidence: judge "it really got created" by the project count going from 0 to 1, not by the agent's own account; force-refresh before screenshotting so stale front-end assets cannot fool you.
- Six-round ledger (the first five were all real failures; none was a problem with the tests):

| Round | What blocked it |
|---|---|
| 1 | `package.json` declared no `@deepseek-ai/dsh-tools` peer → the host loader never injected it, the `import` always failed, and all six tools were unregistered |
| 2 | Tools returned `warning: undefined` → failed the host's lossless-JSON check, so every call on a repository outside the data root failed |
| 3 | All six tools' `render` returned a string → violated the `ContentBlock[]` contract, `content.some` crashed downstream, all six tools were unusable |
| 4 | `copyFiles` listed files already tracked by git → model judgement drift; replaced with a deterministic guard that drops tracked entries by git index |
| 5 | Packaged skills passed no `source` → the host does not fill it in, so all seven skills failed to register on a real machine |
| 6 | All green: the skill genuinely took effect (the trace showed the skill loading, and the agent ran `git check-ignore` itself), and all seven acceptance groups passed |

The first four (peer / serialization / render / skill `source`) were each "the plugin is simply unusable on a real machine" level and are all fixed. Round 4 no longer relies on the agent behaving: `factory_create_project` drops `copyFiles` entries that the git index already tracks, and round 5 proved the guard fires (the agent passed four tracked files, all were dropped, and the stored `copyFiles` was empty).

### P2 — Autonomy engine (**three levels implemented, committed and verified end to end on a real machine**)

The `autonomy` / `autoStart` / `autoApprove` fields used to hold storage and write validation only, with no code reading them to make a decision. **The engine has landed** (`autonomy.js`); the three semantic levels with one switch replaced the old ids and two switches, and old archives load with a one-time migration (see §2.8):

- **One plugin-level timer**, hosted on the host's timer service and torn down with the plugin; a missing service never degrades silently — the reason is readable in `status.engine.timerReason`. Multiple projects are enumerated each tick, not given a timer each; ticks are single-flight and never overlap.
- **`you-approve` takes exactly one automatic edge** (with its `autoDispatch` switch on): `inbox -> triage`, through `dispatchCard`, recorded as `autoRule` with `tier` / `rule` / `channel`. Stage advancement still belongs to the in-session skills acting as `agent` — **the engine never moves a card itself**; the chain stops at `plan-review`. **The agent preset must be mounted explicitly**: dispatched sessions never used to mount a preset, so they had no `tool-bash`, fell back to the host's global SSH tool, and were outside the sandbox's control. They now call `agentPresets.mount(agentCtx)` in `setup` (**with no id, following the user's currently selected preset**) and refuse dispatch if that service is unavailable — a real bug, now fixed. Skill guidance and in-skill body injection are also in place.
- **No switch leaks a capability**: the only switch is `autoDispatch`, read only under `you-approve`; `machine-approve` reads no switch at all (the level is the source of truth) and `manual` is a strict no-op — so "a switch is on, so the code might as well use it" has no path.
- **Two concurrency ceilings** (per project plus a global backstop), counted by live sessions rather than the `sessionId` field; when full, cards queue without being dropped or marked stalled, and a later tick picks them up once a slot frees.
- **Pause / resume / per-card takeover** are three separate actions, each persisted and each leaving a governance record. In the UI, pause is a state switch (on = paused, off = running, label fixed) rather than an action button; pause and takeover both **leave running sessions alone** and only affect later ticks — killing a session outright would leave a worktree and half-finished changes behind.
- **Zero side effects by default**: `manual` does strictly nothing; a project missing its issue source or target board is skipped with the reason visible in `status` — **no guessing, no reverse-engineering the git remote at runtime, no creating a board automatically**. Repository detection is a separate, read-only step that runs only when a person creates a project (§2.6); it is not engine behaviour.
- **Sync does not approve for you**: `sync.js` uses a separate `syncRule` actor plus an empty `SYNC_AUTO_EDGES` allowlist, so a remote "PR closed" suggestion is only recorded for a human and never pushes a waiting card into `build`; plan approval under `machine-approve` uses the `autoRule` actor instead, kept distinct from sync.
- **The permission level is never overclaimed**: `permissionEnforced` is always `false`, and neither the interface nor the status may claim write restriction is in force.
- **Three hard sandbox guarantees** (every level of the dispatch and continuation chains passes the same gates): ① write `sandbox/mode: workspace-write` into `createSession`'s `seed` to pin the mode (no timing race); ② read back the `sandboxMode` projection after creation and refuse/dispose on mismatch; ③ cap the permission at `workspace-write`, never granting a higher project-configured level. Sessions created before the fix are refused on continuation and fall back to a rebuild; old full-access sessions are never reused.

**Verification status**: offline cases plus real-machine checks (the `status.engine` fields, pause/resume, the takeover route, the audit route) are done. **Real automatic dispatch (AE-2) has now been verified end to end on a real machine**: a real GitHub issue was discovered and turned into a card, the engine took the single automatic edge `inbox -> triage` as `autoRule`, and the dispatched agent carried the card through `triage` and `plan` and stopped at `plan-review` — the whole chain ran without a human click. ### P3 — `machine-approve`: machine-assisted plan approval (**implemented and verified on a real machine**)

An **explicit per-project level choice** (never the default, no allowlist, and no switch is read): the machine may approve a plan, taking one more automatic edge `plan-review -> build` as `autoRule` through the same `assertTransition` gate used by every other move, then resumes that card's session so `build` actually runs. The boundary is deliberately narrow — **the machine only approves the plan and resumes its session**:

- After approval it continues the card's session so `build` runs; **arming the delivery authorization still belongs to a person**, and the machine never touches git, opens a pull request, merges or marks done. This is a narrower scope than the original idea of the machine also arming delivery — that part is deliberately not built, a chosen boundary and not a gap.
- Approval and dispatch draw from one concurrency budget (a project ceiling and a global backstop over live sessions). Approving into a `build` with no agent is useless, so when no slot is free the **approval is held with the card**: it remains in `plan-review`, is reported as held for capacity, and a later tick retries. Only a continuation that genuinely opens a new session is charged; a followup onto a still-live session reuses an already counted session and is free. A session that dies between the tick-start liveness scan and the approval decision is re-checked at the decision point, so it cannot bypass the cap.
- `pause` (project or global) and per-card `takeover` block approval immediately and do not replay cards skipped during a pause; repeated ticks stay idempotent; the automatic edge has no bypass to `done`.
- `manual` and `you-approve` never approve plans: approval is the `machine-approve` capability alone, and it checks no switch.

Verified on a real machine: under `machine-approve` a waiting `plan-review` card was approved into `build` with a full audit trail (approval, dispatch and intake events all carry the level's tier); `you-approve`/`manual` stayed inert; pause, takeover and idempotence held; no bypass to `done`; and the AE-2b sync path did not regress. This is **the second half of the autonomy key** — plan approval handed to the machine, delivery authorization still held by a person.

## 6. Research basis (summary, so it is not researched twice)

This plugin does not fork any existing implementation. It compared two reference implementations and took the best of each:

- **Reference A (a kanban-style plugin)**: mature at binding each card to its own session, treating a column move as a stage instruction to the agent, worktree isolation with a dirty check before cleanup, and a background trio (watchdog breaker / cost metering / scheduled jobs). But it **supports only one project root**, and has no plan-approval gate.
- **Reference B (a factory-style framework)**: a multi-source delivery platform of project → board → stage, with an explicit "plan → submit for approval → build" gate and independent review discipline. The cost is that its logic is compressed into a very large runtime dependency and hard-bound to external databases, queues and sandbox vendors.

Conclusion: **take the skeleton from A** (card = own session, worktree isolation, watchdog), **the gate and review discipline from B**, and **build multi-project support ourselves** (A cannot do it, and B's way of doing it is too heavy for a single machine).

The wider comparison that followed — feature strengths and weaknesses across several factory-style products, the Mastra Factory UI anchor, and what later phases should adopt or skip — lives in [RESEARCH.md](RESEARCH.md) / [RESEARCH.zh-CN.md](RESEARCH.zh-CN.md). Its conclusions feed the phases in §4; it is a decision input, not a restatement of this section.

## 7. How to contribute

- Read the conventions at the repository root and in the plugin directory before touching code.
- Before changing anything, confirm which priority it belongs to. All phases in §4 (P1–P7) are complete; re-prioritise against the current §4 status, not against an older one.
- **Write self-contained acceptance assertions**: assert this iteration's added content, cross-copy byte consistency, placeholder sets and real API readback; do not freeze a total and do not use pre-commit file contents as a baseline — once the tests are committed the baseline flips and the commit gate goes red.
- Any change that performs a git write must go through the human approval gate; tests must not bypass it.
- Tests are maintained by a dedicated owner and are not self-certified; numbers come from an actual run, never from "it looks like it runs".
- **Any test that touches the data root injects a temporary `DSH_HOME`**: point it at a directory under `tmpdir()`, then restore the original value and delete it. Never write the real data root, and never sidestep with `skip` — the data-root lookup is lazy, so changing the environment variable inside the process takes effect immediately; the cases really run, which covers more than skipping them would.
- **For "a session does not respond", confirm the agent is actually reasoning before editing the prompt**: two of AE-2's four runs went into prompt changes (skill guidance, inlined skill body) with zero change in real-machine behaviour; the cause was further downstream (model routing / execution mechanism). Investigate in this order: confirm the new code is in memory (`build`) → whether the session produced another turn → whether any tool was called → whether model routing is wired → only then prompt content. Changing prompts before the first four checks is burning real sessions to guess.
- **Real-machine verification must use a repo whose content matches the task**: point the project root at a repo that actually contains the source the task concerns — never a minimal repo with only an empty README. The worktree is created from the project root; if the root has no code, the agent can only clone the real source elsewhere to investigate, and any conclusion about "stays in the worktree" or "reports back" is invalid — and gets misread as a product defect. Fix the fixture before drawing conclusions from a fixture/task mismatch.
- **Wait for `turn/end` to settle before cleaning up evidence**: the criterion is `turn/end.reason.kind` (`error` means aborted/interrupted), **not** the later `session/end` / `job/settled:completed` — those are post-crash cleanup events, not evidence of a normal finish. Deleting the worktree early removes the agent's cwd and prevents it from completing "write report + advance card"; it then looks like "no report back" when it was actually interrupted. Clean up only after the turn truly ends (or fails explicitly).
